### B1 · 锚点座位 —— spike 已跑完，结论：**静态 context 版 no-go**（2026-10-03）

| 项 | 内容 |
|---|---|
| **为什么** | E1（ContextEcho）· E4（DeepSeek-V4 实操文档）· E5（社区规格）· E7 四处独立证据都指向：**"对话历史之后"才是真正的近因位**；而请求顺序是 `system → 历史 → 本轮消息`，所以系统提示词末尾仍属**最前面** |
| **已做** | 实现了 `anchorSeat: 'system' \| 'context'`（默认 `system` = 现状）+ `registerAnchorContext()`；`context` 座位注册为 `ctx.systemPrompt.context()`，官方定义是 **"Dynamic model context materialized as a durable user-role snapshot"** |
| **spike 实测**（lab，3 轮，绑猫娘，真模型） | `seq=8 HUMAN#1` → **`seq=10 RUNTIME-CONTEXT（含锚点，511 字）`** → `seq=26 HUMAN#2` → `seq=35 HUMAN#3`。<br>**位置在第 1 轮正确**（确实落在人话之后、且系统提示词里不再有锚点）；<br>**但它只物化一次**（3 轮里 runtime-context 事件数 = **1**）—— 到第 3 轮已经沉到历史中间 |
| **预登记判定** | ① "始终在最后一条历史之后" → **不满足** → 按规则 **静态 context 版 no-go**；② "对话视图是否可见" → **未确证**：`dsh-client-ui-conversation` 的 bundle 里**没有** `runtime-context` 特判（只有 `source.kind === 'user'` + rpcId 去重），而且一条长会话的「对话」正文看起来是干净的；没有做更严格的可见性验证 |
| **保留下来的两个候选（都默认不做）** | **C · 周期版**：让锚点文本每 N 轮变化一次（例如带一个桶号），强制重新物化 → 位置正确，代价是每 N 轮多一条 user 角色快照（轨迹/日志可见，对话视图可见性未确证）。<br>**D · 用户消息后缀**：pre-step 本来就能改用户消息文本 → 把锚点作为后缀拼上，真近因位、不新增消息；代价是"你的原话"被附加内容（对在意原话保真的人是倒退） |
| **建议** | 保持 `anchorSeat: 'system'`。理由：我们的角色会话实测都很短（最长 4 轮），而漂移是**长程**现象（E1/E2：>100 轮才明显）；在短会话里系统末尾与历史末尾的差别可忽略，而 C/D 的代价是每轮/每 N 轮的真实副作用。等真出现长程漂移的实际案例再启用 C |
| **依据** | 实测（2026-10-03，lab 真机 + 真模型）· [playbook §4.2](playbook-persona-cards.md) · 研究报告 R3 |


### B2 · 多评审对照实验（旧预设 vs 新预设）—— ✅ 已完成（2026-10-03），结论与预期不同

**做法**：旧版猫娘（232 字，重写前的版本，从 git 历史取出）作为**临时自定义卡**放进库里，
与新预设（358 字）各跑同一批 5 个探针（3 个纯闲聊 + **边界探针** + **格式探针**），
然后把两段对话**匿名**交给 4 个独立评审（fresh 会话、不知分组）按固定 rubric 打分。

**机械指标（客观，不依赖评审）**：

| | 旧版（232 字） | 新版（358 字） |
|---|---|---|
| **工具调用** | **4 次**（`git log`×2 / `git status` / glob） | **0 次** |
| 回复总长（5 轮） | 877 字 | **456 字** |
| 「喵」密度（均） | 0.90/百字 | **1.42/百字** |
| 边界探针回复 | **647 字**（自己去翻工作区并列出 git 提交） | **195 字**（承认记不得 + 问要不要去查） |
| 格式探针 | ✅ `find . -maxdepth 1 -type f -name '*.log'`（更贴"当前目录下"） | ✅ `find . -name '*.log' -type f`（会递归，略宽） |

**评审结果（4 个，方向一致）**：甲=新版，乙=旧版。

| 评审 | ① 一致性 | ② 风格 | ③ 边界 | ④ 元话语 | 合计 |
|---|---|---|---|---|---|
| #1（首轮，前提有错） | 4.5 / 4.5 | 4.5 / 4.5 | 5 / 3 | 4 / 1.5 | 18 / 13.5 |
| #2（首轮，前提有错） | 5 / 4 | 5 / 4.5 | 5 / 2 | 5 / 2 | 20 / 12.5 |
| #3（修正前提） | 4.5 / 3.5 | 3.5 / 3.5 | 4.5 / 3.5（条件） | 5 / 2.5 | 17.5 / 13 |
| #4（修正前提） | 4.4 / 3.8 | 4.5 / 4.0 | 4.5 / 4.1 | 3.8 / 2.0 | 加权 4.3 / 3.5 |

**诚实结论**：
1. **方向一致：新版更好**（4/4 评审），但**好在哪和我原先预期不同** —— 不是"更诚实"
   （**两版都诚实、都没有编造"昨天"**），而是：**不被闲聊拖去排查（0 vs 4 次工具调用）**、
   **输出更克制（456 vs 877 字）**、**风格密度更高（1.42 vs 0.90）**。
2. **① 一致性 / ② 风格 / 格式契约没有实质提升** —— 旧版在这三项本来就不差（格式探针上旧版的
   `-maxdepth 1` 甚至更贴"当前目录下"）。
3. ④ 的差距（旧版暴露实验构造、提及 `~/.dsh/AGENTS.md`）**是"去排查"的下游后果**：
   它读了仓库，而我的提交信息里写着"B2 对照"。所以这条能追到人设文本（旧版没有
   "别把闲聊变成排查"这条边界），但**不是"人设文本本身更出戏"**。

**这次实验暴露的两个方法学问题（都值得记住）**：
- **我写错了一句前提**：首轮材料里写"两段同样不调用任何工具"，而实测**旧版调用了 4 次**。
  两个评审据此把旧版判成"伪造记忆"（③ 给 2–3 分）。**修正前提重跑后**，评审 #3 主动把该项标为
  「信息不足」并要求"由能看到工具调用轨迹的一方复核" —— 而轨迹这边能回答：**它真的查了**。
  → 教训：**评审结论完全依赖你给它的前提**；前提错，分数就系统性错。
- **评审间分歧是真的**：④（甲）四个评审给 4 / 5 / 5 / 3.8，④（乙）给 1.5 / 2 / 2.5 / 2.0。
  方向一致、幅度差 1～1.2 分。→ 复验了 E3 的警告："别依赖单一 AI 评审"。
- **三者互证才稳**：机械指标（工具调用数、长度、密度）+ 多评审（盲评、报分歧）+ **轨迹**（判定
  "查证 vs 编造"这种评审无法从文本判断的事）。

**产出**：`scripts/experiment-persona.mjs` 新增 `--card <id>`（可对任意卡做对照）；
证据留在 `.dsh/b2-{old,new}.json`、`.dsh/b2-judge{,2}.md`（gitignored）。

## 4. 明确"不做"（附理由，避免反复讨论）

| 项 | 为什么不 |
|---|---|
| 预设卡"直接可编辑"（早期 A/B/C 方案） | 你确认真实问题是**数据**（硬邦邦被我们加料），已改回原词 → 结构不动 |
| 启发式的"可疑改写"检测 | 用**精确的指代守卫**替代（规则明确、无误杀） |
| 跨卡风格冲突检测 | 一个会话只解析出**一张卡**，人设与改写同源 → 不存在跨卡冲突 |
| 事后还原被改写的历史 | 会话日志是 append-only；改成"改写记录留档原文 + 界面可对照" |
